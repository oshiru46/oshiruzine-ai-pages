Claude Code/Codexでのソフトウェア開発の最新ベストプラクティス

2026年も後半に入り、AIコーディングエージェントはもはや「試してみる」段階を完全に超えた。ターミナルに常駐するClaude Codeと、非同期でタスクを処理するOpenAI Codexは、開発チームの標準ツールチェインに組み込まれつつある。しかし、導入したチームの間で成果に大きな差が生まれていることも事実だ。うまく使いこなすチームと、「結局手で書き直している」チームの間にある決定的な違いは何か。本コラムでは、2026年9月時点での最新動向を踏まえ、実務で即使えるベストプラクティスを整理する。

エージェント型開発の現在地

2026年前半、Anthropicは Claude Code にマルチファイル横断のコンテキスト理解とテスト自動生成機能を大幅に強化した。一方のOpenAI Codexも、2026年6月のアップデートでCodex-2モデルへの移行が完了し、リポジトリ全体の構造を把握したうえでの変更提案精度が飛躍的に向上している。両者に共通するのは、単なるコード補完ツールから「意図を理解して自律的にタスクを遂行するエージェント」へと進化した点だ。

この変化は開発者の役割にも影響を与えている。プロンプトを打ち込む「指示者」ではなく、AIエージェントの出力をレビューし、アーキテクチャ判断を下す「監督者」としてのスキルセットが求められるようになった。

プロンプト設計：指示ではなく「制約」を与える

最も成果を分けるポイントが、プロンプトの設計思想だ。初期の頃は「○○の関数を書いて」という直接的な指示が主流だったが、現在のベストプラクティスは制約ベースのプロンプティングに移行している。

具体的には、以下のような要素をプロンプトに含める。

  • 技術的制約：使用するフレームワーク、言語バージョン、依存ライブラリの範囲
  • 品質基準：テストカバレッジの目標値、パフォーマンス要件、セキュリティポリシー
  • 禁止事項：使ってほしくないパターン、避けるべきライブラリ、非推奨API

たとえば Claude Code では CLAUDE.md ファイルにプロジェクト固有のルールを記述しておくことで、セッションをまたいでも一貫した出力が得られる。2026年8月のアップデートで導入された階層型メモリ機能により、リポジトリ・ディレクトリ・ファイル単位でコンテキストを自動的に切り替える仕組みも実用段階に入った。

テスト駆動でAIを制御する

AIエージェントの出力品質を担保するうえで、最も効果的なのがテスト駆動開発（TDD）との組み合わせだ。これは単なる開発手法の推奨ではなく、AIの出力を検証可能な形で制約する仕組みとして機能する。

ワークフローとしては次の流れが推奨される。

  1. 人間がテストケースを先に書く（あるいはAIに書かせてレビューする）
  2. AIエージェントに実装を委ねる
  3. テストがパスするまでAIが自律的に修正を繰り返す
  4. 人間がコードレビューで最終判断を下す

Claude Code の /test-loop コマンドや Codex の自動修正モードは、このサイクルを自動化する。実際に、GitHub上の大規模OSSプロジェクトでもこのパターンの採用が急速に広がっており、2026年のState of AI Coding調査では、エージェント活用チームの72%がTDDベースのワークフローを採用していると報告されている。

セキュリティとガバナンス：見過ごせない論点

生産性向上の裏で、セキュリティリスクへの対応も進化している。2026年に入り、AIが生成したコードに起因する脆弱性インシデントの報告が複数件公表されたことを受け、各ツールともガードレール機能を強化した。

Claude Code では、生成コードに対するリアルタイムの脆弱性スキャンがデフォルトで有効化され、既知のCWE（Common Weakness Enumeration）パターンに該当するコードは警告付きで出力されるようになった。Codex側でも、組織ポリシーに基づいたコード生成制約をAPI経由で設定できる Enterprise Policy Engine が正式リリースされている。

チームとして押さえておくべきポイントは以下の3つだ。

  • 生成コードのSBOM（Software Bill of Materials）管理：AIが暗黙的に導入する依存関係を可視化する
  • プロンプトインジェクション対策：外部入力をそのままプロンプトに渡さない設計を徹底する
  • 監査ログの保持：誰がどのプロンプトでどのコードを生成したかをトレーサブルにする

Claude Code vs Codex：使い分けの勘所

「どちらを使うべきか」は最もよく聞かれる質問だが、2026年9月時点での実用的な答えは「タスク特性で使い分ける」だ。

Claude Code は対話的な探索と設計判断を伴うタスクに強い。アーキテクチャの検討、リファクタリング方針の策定、複雑なバグの原因調査など、人間との協調作業が必要な場面で真価を発揮する。一方の Codex は、明確に定義されたタスクの非同期バッチ処理に向いている。大量のボイラープレート生成、定型的なマイグレーション作業、テストの一括生成といったシナリオではスループットの面で優位だ。

最近では、両者を CI/CD パイプライン内で併用するハイブリッド構成も増えている。PRが作成されると Codex がテストを自動生成し、Claude Code がコードレビューコメントを付ける、といったワークフローだ。

まとめ：人間の判断力がますます重要になる

AIコーディングエージェントの能力が上がるほど、逆説的に人間の判断力の価値が高まっている。どの制約を与えるか、どのテストを書くか、どのアーキテクチャを選ぶか——これらの意思決定こそが、ソフトウェアの品質と保守性を決定づける。ツールは日々進化し続けるが、「何を作るべきか」「なぜそう作るのか」を考える力は、依然として開発者の最も重要な資産である。最新のツールを最大限に活かすために、まずは自分たちのプロジェクトの制約と品質基準を言語化するところから始めてみてほしい。

マルチモーダルエージェントの現在地──GUI操作・物理世界へ拡張するAIの最前線

「AIにブラウザを操作させて、航空券を予約してもらう」──1年前なら研究デモの域を出なかったこのシナリオが、2026年夏、ついに商用SaaSの一機能として提供され始めた。Anthropicの「Computer Use」が火をつけたGUI操作エージェントの波は、OpenAI、Google DeepMind、そしてスタートアップ群を巻き込みながら急速に拡大し、さらにロボティクスとの統合という次の地平へと踏み出している。テキストチャットの枠を超え、画面のピクセルを「見て」クリックし、センサーデータを「感じて」ロボットアームを動かすマルチモーダルエージェントは、いまどこまで来ているのか。本稿では、技術スタック・主要プレイヤーの最新動向・実運用の課題と設計パターンを体系的に整理する。

テキストの先へ──マルチモーダルエージェントとは何か

マルチモーダルエージェントという用語は、単に「画像も扱えるLLM」を指すわけではない。ここでの定義は明確だ。テキスト・画像・音声・センサーデータなど複数のモダリティを入力として受け取り、デジタルまたは物理環境に対して自律的にアクションを実行するAIシステムである。

従来のLLMベースアシスタントは「テキストイン・テキストアウト」が基本だった。ツール呼び出し（Function Calling）でAPIを叩くことはできたが、あくまで構造化されたインターフェースを経由していた。2025年後半からの転換点は、非構造化インターフェース──すなわちGUIのスクリーンショットやカメラ映像──を直接理解して操作する能力が実用水準に達したことにある。

この進化を支えるのが、Vision-Language-Action（VLA）モデルと呼ばれるアーキテクチャの成熟だ。視覚入力を言語的推論と結びつけ、具体的な行動（マウスクリック座標の指定、ロボット関節角の出力）を生成する。2026年に入り、このVLAモデルがGUI操作とロボティクスという二つの領域で同時に花開いている。

GUI操作エージェントの技術スタック

スクリーンショット理解からアクション生成まで

Computer Use系エージェントの基本アーキテクチャは、以下の4層で構成される。

  1. 画面キャプチャ層：対象アプリケーションのスクリーンショットを定期的に取得する。OS標準のスクリーンキャプチャAPI、あるいはブラウザの場合はCDP（Chrome DevTools Protocol）を利用する。
  2. 視覚理解層：キャプチャされた画像をVision-Language Model（VLM）が解析し、UI要素の位置・種類・状態を認識する。2026年現在、Gemini 2.5、Claude 4（Sonnet/Opus）、GPT-5がこの領域でしのぎを削っている。
  3. 推論・計画層：現在の画面状態とユーザーの目標を照合し、次に取るべきアクション（クリック、タイプ、スクロールなど）を決定する。Chain-of-Thought推論やReActパターンが標準的に用いられる。
  4. アクション実行層：決定されたアクションをOS/ブラウザに対して実行する。座標ベースのマウス操作、キーボード入力、あるいはアクセシビリティAPIを通じたセマンティック操作が選択肢となる。

Set-of-Markプロンプティングの進化

注目すべき技術的ブレークスルーの一つが、Set-of-Mark（SoM）プロンプティングの第2世代だ。画面上のインタラクティブ要素に番号付きバウンディングボックスを重畳表示し、モデルに「要素7をクリック」と指示させる手法は2024年に登場したが、2026年にはこの手法がさらに洗練された。動的に生成されるUI要素（ポップアップ、ドロップダウン）への対応、スクロール外要素の推論、そしてアクセシビリティツリー情報との統合により、操作精度は大幅に向上している。

Anthropicが2026年6月に公開した内部ベンチマーク「WebArena-v3」では、Claude 4 Opusのタスク完遂率が78.3%に達した。これは1年前のClaude 3.5 Sonnetの約42%から倍近い飛躍であり、「人間の監督下であれば実運用に耐える」水準と評価されている。

さらに注目すべきはGemini Roboticsの動きだ。2026年3月に発表されたGemini 2.5ベースのロボティクスモデルは、自然言語指示から直接ロボットの低レベル制御コマンドを生成する。Google傘下のEveryday Robotsチームとの統合により、物流倉庫でのピッキング作業での実証実験が進行中だ。

ロボティクス領域では、Figure社との提携が新たなフェーズに入っている。Figure 02ヒューマノイドロボットに搭載されたGPT-5ベースのVLAモデルは、「この棚の赤い箱を取って、テーブルの上に置いて」といった自然言語指示をリアルタイムで解釈・実行する。2026年のBMW工場での本格導入が業界に衝撃を与えた。

物理世界への拡張──ロボティクスとの統合

VLAモデルの成熟

GUI操作がデジタル世界のエージェントであるなら、ロボティクス連携は物理世界のエージェントだ。この二つを統合するのがVLAモデルである。

2026年の技術的な画期は、ゼロショット汎化能力の劇的な向上にある。従来のロボティクスモデルは、学習時に見たオブジェクトや環境にしか対応できなかったが、大規模VLAモデルは事前学習で獲得した世界知識により、未知の物体や環境でも合理的な操作戦略を生成できるようになった。

RT-2（Robotics Transformer 2）の系譜を継ぐGoogleのRT-Xプロジェクト、そしてToyota Research InstituteとMITの共同プロジェクトが発表した拡散ベースの行動生成モデルは、いずれも「言語で指示し、視覚で理解し、行動で応える」というVLAパイプラインの実用性を示している。

シミュレーションからリアルワールドへ

Sim-to-Real転移（シミュレーション環境で学習したポリシーを実環境に移す技術）も急速に進化している。NVIDIA IsaacシミュレータとOmniverse上での大規模並列学習、そしてドメインランダマイゼーション技術の改良により、シミュレーションで訓練したエージェントが実環境で動作する成功率は90%を超えるケースも出てきた。

実運用における課題と設計パターン

技術の成熟は著しいが、実運用に耐えるシステムを構築するには、依然として複数の課題が存在する。ここでは実務者が直面する主要な論点と、それに対する設計パターンを整理する。

課題1：エラーリカバリとフォールバック

GUI操作エージェントは、予期しないポップアップ、ネットワーク遅延によるページ未ロード、CAPTCHAなど、想定外の状態に頻繁に遭遇する。

設計パターン：チェックポイント＆ロールバック方式。各操作ステップでアプリケーション状態のスナップショットを保存し、エラー検知時に直前の安定状態へロールバックして再試行する。さらに、一定回数の再試行後は人間にエスカレーションする「Human-in-the-Loop」フローを組み込むことが、現時点でのベストプラクティスだ。

課題2：セキュリティとサンドボックス化

エージェントにGUI操作権限を与えることは、事実上「画面の前に座っている人間と同等の権限」を与えることを意味する。誤操作によるデータ削除、意図しない送金、機密情報の漏洩といったリスクは深刻だ。

設計パターン：最小権限サンドボックス＋承認ゲート。エージェントは隔離された仮想デスクトップ環境（Docker + VNC、あるいはクラウドブラウザ）で実行し、金銭取引や不可逆操作の前には人間の明示的承認を要求するゲートを設ける。Anthropicが提唱する「Constitutional AI for Agents」の考え方──エージェントに憲法的なルールセットを埋め込む──も有力なアプローチだ。

課題3：レイテンシとコスト

スクリーンショットの取得→VLM推論→アクション実行→次のスクリーンショット、というループは、1ステップあたり2〜5秒を要する。10ステップのタスクで30〜50秒。人間なら15秒で終わる操作が、エージェントでは数倍かかるケースも珍しくない。

設計パターン：ハイブリッドアプローチ。構造化APIが利用可能な箇所ではAPIを直接呼び出し、GUIでしか操作できない箇所のみ視覚ベースの操作を行う。加えて、頻繁に実行するワークフローは操作ログから「マクロ」を自動生成し、VLM推論を介さない高速パスを用意する。

課題4：評価とモニタリング

エージェントの「正しさ」をどう評価するかは、未解決の難問だ。タスク完遂率だけでなく、操作効率（ステップ数）、安全性（禁止操作の回避）、そしてユーザー意図との整合性を多角的に評価する必要がある。

設計パターン：オブザーバビリティ・スタック。各ステップのスクリーンショット、モデルの推論ログ（思考過程）、実行アクションを時系列で記録し、事後分析可能なダッシュボードを構築する。LangSmithやArize Phoenixなどのエージェント観測ツールが、この領域で急速に機能拡充を進めている。

2026年後半以降の展望

マルチモーダルエージェントの進化は、2026年後半にさらに加速する兆候を見せている。

統合プラットフォームの出現が一つの大きな流れだ。GUI操作・API呼び出し・ロボット制御を単一のエージェントフレームワーク上で統合管理するプラットフォームが、LangChain、CrewAI、Microsoft AutoGenなどのOSSプロジェクトから登場しつつある。とりわけMicrosoftがBuild 2026で発表した「Windows Copilot Agent SDK」は、OS レベルでのエージェント統合を推進するものとして注目度が高い。

マルチエージェント協調も次のフロンティアだ。単一のエージェントでは困難な複雑タスクを、役割分担された複数のエージェントが協調して遂行する。調査エージェントがWeb検索で情報を集め、分析エージェントがスプレッドシート上でデータを整理し、報告エージェントがドキュメントをまとめる──こうしたオーケストレーションの実用例が増えている。

そして規制・標準化の動きも見逃せない。EUのAI Actが2026年8月に全面施行となり、自律エージェントのリスク分類と透明性要件が明確化された。日本でも経済産業省が「AIエージェントガイドライン」の策定を進めており、年内の公開が予定されている。技術の進化と社会実装のバランスをどう取るかは、エンジニアと研究者が当事者として関わるべきテーマだ。

マルチモーダルエージェントは、AIが「考える」存在から「行動する」存在へと転換する、パラダイムシフトの只中にある。テキストプロンプトを打つだけのAI利用は、振り返ればほんの序章に過ぎなかった。画面を見て、クリックし、物理世界のモノを動かす──その能力を持ったAIと、私たちはどう協働するのか。2026年の今、その問いに対する答えは、まさにリアルタイムで書き換えられている。

AI規制の世界地図2026秋──EU AI Act全面施行後の実務インパクト

2026年8月2日──この日を境に、AIの開発現場は明確に「Before」と「After」に分かれた。EU AI Actの汎用AIモデル（GPAI）規制が全面適用となり、欧州市場にサービスを提供するすべてのAI開発者が、リスク分類・透明性要件・文書化義務という"三重の壁"に直面している。日本のスタートアップから大手SIerまで、「対岸の火事」と見ていた企業が慌ただしく対応に動き始めた今、各国の規制アプローチを俯瞰し、エンジニアが開発プロセスの中で何をすべきかを整理しておきたい。

EU AI Act全面施行──何が変わったのか

2024年8月に発効したEU AI Actは、段階的に適用範囲を拡大してきた。2025年2月には禁止AIの規定が適用開始となり、ソーシャルスコアリングや感情認識の無断利用といったカテゴリが明確に禁じられた。そして2026年8月、いよいよ本丸であるGPAI規制と高リスクAIシステムに関する義務が全面的に効力を持った。

  • 技術文書の作成・維持：モデルの学習データ、アーキテクチャ、評価結果を含む包括的ドキュメントの整備

エンジニアが開発プロセスで対応すべき3つの実務ポイント

規制の全体像を把握したうえで、開発現場では具体的に何をすべきか。以下の3点に集約される。

1. リスク分類の早期判定をパイプラインに組み込む

EU AI Actは「許容できないリスク」「高リスク」「限定リスク」「最小リスク」の4段階でAIシステムを分類する。プロジェクトの企画段階で、自社のシステムがどのカテゴリに該当するかを判定するプロセスを設けることが不可欠だ。特に高リスクに分類されるのは、採用選考、信用スコアリング、法執行、重要インフラ管理など、Annex IIIに列挙された領域だ。判定を後回しにすると、リリース直前で大幅な手戻りが発生するリスクが高い。

2. 透明性要件への対応を設計段階から実装する

GPAIモデルを利用したシステムでは、AIが生成したコンテンツであることの明示（ウォーターマーキング等）、モデルカードの公開、利用規約における制限事項の明記が求められる。これらは後付けではなく、アーキテクチャ設計やCI/CDパイプラインの中に組み込むべきだ。C2PA（Coalition for Content Provenance and Authenticity）規格への対応も、ディープフェイク規制との関連で事実上の標準になりつつある。

3. 文書化を「負債」ではなく「資産」として運用する

技術文書の作成は面倒な規制対応コストと見なされがちだが、モデルの学習データ来歴、評価メトリクス、バイアス検証結果などを体系的に管理することは、本来エンジニアリングの品質向上に直結する。MLOpsの文脈で普及しているModel Registry やExperiment Trackingツールを拡張し、規制対応文書を自動生成する仕組みを構築している先進企業も出てきている。文書化を技術的負債ではなく、再現性とガバナンスのための資産と捉え直すことが、長期的な競争力の源泉になる。

規制は制約ではなく設計要件である

AI規制を取り巻く世界地図は、2026年秋の時点でかつてないほど複雑化している。しかし、その本質は「信頼できるAIを社会実装するための設計要件」にほかならない。GDPRがプライバシー・バイ・デザインを当たり前にしたように、AI Actはリスク管理・透明性・説明責任をAI開発の標準プラクティスへと押し上げようとしている。

エンジニアに求められるのは、規制文書を読み込む法務的スキルではない。リスク分類を設計判断に反映させ、透明性をアーキテクチャに織り込み、文書化をパイプラインに統合する──そうした「規制対応を技術で解く」姿勢だ。各国規制の動向は今後も流動的であり続けるが、信頼性と透明性を志向する大きな潮流は不可逆である。その潮流の中で、技術者としてどうシステムを設計するか。いま問われているのは、まさにその設計思想そのものだ。

1. モデル蒸留──"小さな優等生"を仕立てる

大規模な教師モデルの出力を使い、パラメータ数が1/10〜1/20の生徒モデルを訓練する手法。2026年前半にはGemma 3nやLlama 4 Scoutなど、蒸留前提で設計された軽量アーキテクチャが相次いで公開され、タスク特化の蒸留パイプラインが急速に整備された。自社データで教師の合成出力を作り、7〜12Bクラスに蒸留するだけで、品質を90%以上維持しながらコストを5〜10分の1に落とせるケースが報告されている。初期の訓練コストはかかるが、リクエスト数が多いサービスほど回収が早い。

2. 量子化──4bitは当たり前、2bitの実用域が見えてきた

GPTQ・AWQ系の4bit量子化は既にコモディティ化した。注目すべきは2bit/1.58bit量子化の進展だ。BitNet b1.58の流れを汲む研究が実用レベルに近づき、70Bモデルを単一GPU（VRAM 24GB）で動かすデモが増えている。精度劣化はRAG併用やプロンプト工夫である程度吸収可能で、レイテンシ改善との一石二鳥が魅力。ただし長い推論チェーンや数学タスクでは品質低下が顕著なため、タスクプロファイリングが必須だ。

3. MoEルーティング──全パラメータを起こさない知恵

Mixture-of-Expertsは、巨大モデルの一部のエキスパートだけを活性化することで、実効FLOPsを総パラメータの10〜20%に抑える。Mixtral以降、DeepSeek-V3やLlama 4 Maverickなど数百B〜兆パラメータ級MoEが主流になりつつある。API提供側もアクティブパラメータ数ベースで課金するモデルが増え、ユーザから見たコスト構造が劇的に変わった。自前ホスティングではエキスパート単位のオフロード戦略がカギになる。

4. スペキュラティブデコーディング──"下書き＋検算"の高速化

小型ドラフトモデルで複数トークンを先行生成し、大型モデルで一括検証する手法。スループットが2〜3倍に向上するため、同一品質を維持しながらGPUあたりの処理量を増やせる。Medusaの多ヘッド拡張やEAGLE-2系の投機ツリー探索が成熟し、vLLMやTensorRT-LLMへの統合も進んだ。既存パイプラインへの追加が比較的容易な点も実務向きだ。
