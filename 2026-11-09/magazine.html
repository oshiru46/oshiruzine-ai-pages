Claude Code/Codexでのソフトウェア開発の最新ベストプラクティス

2026年も終盤に差し掛かり、AIコーディングアシスタントの勢力図は大きく塗り変わった。中でもAnthropicの「Claude Code」とOpenAIの「Codex」は、単なるコード補完ツールから"開発パートナー"へと進化を遂げ、多くのエンジニアの日常ワークフローに深く組み込まれている。しかし、ツールの進化が速すぎるがゆえに「なんとなく使っている」状態のチームも少なくないのではないだろうか。本稿では、2026年後半時点での両ツールの最新動向を踏まえ、実務で即活用できるベストプラクティスを整理してお届けする。

Claude CodeとCodexの現在地——2026年後半のアップデート概要

Claude Codeは、2025年のローンチ以降急速にアップデートを重ね、2026年中盤にはClaude 4ファミリーのモデルをバックエンドに搭載したことで、長大なコードベースの文脈理解力が飛躍的に向上した。特にターミナルネイティブのインターフェースはそのままに、プロジェクト全体のアーキテクチャを俯瞰しながらファイル横断でリファクタリングを提案・実行する能力は、競合製品を一歩リードしている。加えて、CLAUDE.mdによるプロジェクト固有の指示ファイルの仕組みが成熟し、チーム全体の開発規約をAIに"記憶"させる運用が標準化しつつある。

一方のOpenAI Codexも、2025年のリリースからサンドボックス実行環境の安定性を高め、2026年にはo3ベースのコードリーズニングを強化。マルチファイル編集やテスト自動生成において着実に精度を上げてきた。CLI版のCodexもオープンソースとして公開され、カスタマイズ性の高さがパワーユーザーに支持されている。

両ツールとも「コードを書くだけのAI」ではなくなった。いかに適切に指示を与え、レビューし、開発プロセスに統合するかが成果を分ける時代に突入している。

ベストプラクティス1：コンテキストエンジニアリングの徹底

AIコーディングツールの出力品質を最も左右するのは、モデルの性能ではなく「どのような文脈を渡すか」だ。2026年現在、この領域は「プロンプトエンジニアリング」から一歩進んだ「コンテキストエンジニアリング」として体系化されつつある。

Claude Codeでは、リポジトリルートに配置するCLAUDE.mdが事実上の"AIへの設計書"となる。ここにコーディング規約、アーキテクチャの方針、使用ライブラリのバージョン制約、さらにはやってほしくないこと（ネガティブ制約）まで明記しておくことで、セッションごとの指示のブレを大幅に削減できる。サブディレクトリごとに異なるCLAUDE.mdを階層的に配置する手法も、モノレポ運用のチームで広まっている。

Codexでも同様に、AGENTS.mdやシステムプロンプトのカスタマイズが鍵となる。要は、プロジェクト固有のドメイン知識・制約をいかに構造的にAIへ渡すかの設計力が、開発効率に直結する。

ベストプラクティス2：タスク分割と段階的実行

大きな機能追加を一度に丸投げするのは、2026年のモデル性能をもってしても推奨されない。最も成果が出ているチームが実践しているのは、以下のような段階的アプローチだ。

  1. 計画フェーズ：まず「コードを書かずに設計案だけ出して」と指示し、AIの理解度を確認する
  2. 実装フェーズ：設計案に合意した上で、ファイル単位・関数単位で段階的に実装を指示する
  3. 検証フェーズ：AIが生成したコードに対してテストコードも同時に書かせ、サンドボックスで実行結果を確認させる

Claude Codeのextended thinking機能やCodexの推論トレースを活用すれば、AIが「なぜその実装を選んだか」の思考過程を可視化できる。ブラックボックスのまま受け入れるのではなく、推論過程をレビューする習慣が品質を担保する。

ベストプラクティス3：ヒューマン・イン・ザ・ループの再設計

AIの自律性が高まるほど、逆説的に「人間がどこで介入するか」の設計が重要になる。Claude Codeには権限レベルの設定（--allowedTools等）があり、ファイル書き込みやコマンド実行をどこまで自動承認するかを細かく制御できる。Codexも同様にサンドボックスの権限管理を提供している。

実務上のベストプラクティスとしては、以下の使い分けが定着しつつある。

  • 自動承認してよいもの：リントの修正、型エラーの修正、テストの追加、ドキュメント生成
  • 人間の確認を挟むべきもの：アーキテクチャの変更、セキュリティに関わるコード、外部API連携、データベーススキーマの変更

「AIに任せすぎて気づいたらコードベースが読めなくなっていた」という事例は業界で散見される。AIが書いたコードも、チームの誰かが"オーナーシップ"を持つ——この原則は、ツールがどれだけ進化しても変わらない。

ベストプラクティス4：CI/CDパイプラインとの統合

2026年後半の大きなトレンドとして、AIコーディングツールのCI/CDパイプラインへの本格統合がある。GitHub Actions上でClaude Codeを動かし、プルリクエストに対して自動でコードレビューや軽微な修正提案を行う構成は、もはや先進的な取り組みではなく標準プラクティスになりつつある。Codexについても同様のCI統合パターンが確立されている。

ただし注意点がある。AI生成のコードをCIで自動マージまで行うのは時期尚早だ。現時点では「AIがドラフトPRを作成→人間がレビュー→マージ」というフローが、品質と速度のバランスとして最適解とされている。

まとめ——道具の進化に、使い方の進化を追いつかせる

Claude CodeもCodexも、半年前とはまるで別物と言えるほど進化し続けている。しかし、ツールの性能向上だけに頼っていては、その恩恵を十分に引き出すことはできない。コンテキストの設計、タスクの分割戦略、人間の介入ポイントの最適化、そしてCI/CDとの統合——これらを意識的にアップデートし続けることが、AIネイティブな開発チームとそうでないチームの差を決定的に広げていく。次の半年でさらなる変化が訪れるのは確実だ。今日のベストプラクティスを押さえつつ、常にキャッチアップする姿勢を維持していきたい。

マルチモーダルエージェントの現在地――GUI操作からロボティクスまで、2026年後半の到達点を整理する

「AIに仕事を任せる」という言葉の意味が、この1年で根本から変わった。2025年初頭、私たちがエージェントに期待していたのは、せいぜいチャット上でのタスク分解や API 呼び出しの自動化だった。ところが2026年後半の今、エージェントは私たちと同じディスプレイを見つめ、マウスを動かし、キーボードを叩き、さらには物理的なロボットアームでモノを掴んでいる。Computer Use、Project Mariner、そしてそれらに続く無数のプロダクトが切り拓いた「マルチモーダルエージェント」の現在地を、アーキテクチャ・実用事例・安全性の三つの軸から整理したい。

GUI操作エージェント――"見て・理解して・操作する"が当たり前になるまで

振り返れば、転換点は2024年秋の Anthropic「Computer Use」ベータと、Google DeepMind「Project Mariner」のデモだった。スクリーンショットを視覚的に解釈し、座標レベルでクリックやタイピングを実行するというコンセプトは当時こそ実験的だったが、2025年を通じて各社が猛烈に精度を引き上げた。

2026年に入ってからの進展は加速の一語に尽きる。Anthropic は Claude 4.5 世代で Computer Use を GA（一般提供）に昇格させ、操作遅延を平均 300 ms 以下に短縮した。画面認識の解像度も 4K ネイティブ対応となり、Excel の小さなセル番地を正確にクリックできるレベルに到達している。Google は Gemini 2.5 Ultra ベースの Mariner V2 を Chrome 拡張として正式リリースし、ブラウザ内の複数タブを横断する業務フローの自動化をエンタープライズ向けに展開した。一方、OpenAI は GPT-5 ファミリーに統合する形で「Operator Pro」を今年7月にリリースし、Windows / macOS のネイティブ GUI 操作に対応。Microsoft との協業により、OS レベルのアクセシビリティ API と視覚認識を融合したハイブリッド方式を採用しているのが技術的な特徴だ。

オープンソース側の動きも見逃せない。2026年前半に公開された CogAgent-2 (Tsinghua/Zhipu) は Apache 2.0 ライセンスで商用利用可能な GUI エージェント基盤として急速に普及し、SWE-bench のエージェント版ベンチマーク「SWE-agent-bench v2」でプロプライエタリモデルに肉薄するスコアを叩き出した。また、Hugging Face コミュニティ発の「OpenAdapt 2.0」は、RPA の操作ログを教師データに変換してファインチューニングする仕組みを標準化し、企業固有の業務画面への適応コストを大幅に下げている。

要するに、2026年後半時点でGUI操作エージェントは「動くかどうか」ではなく「どう安定運用するか」のフェーズに入った。

ロボティクスへの展開――身体を持ったエージェントの現在地

GUI操作が"デジタル空間の身体性"だとすれば、ロボティクスは文字通りの身体性だ。ここでもこの1年の進展は目覚ましい。

Google DeepMind は2026年3月に Gemini Robotics モデル群を発表し、RT-2 以来の汎用ロボット基盤モデルの世代交代を印象づけた。特筆すべきは、Gemini のマルチモーダル理解能力をそのままロボット制御に接続する「Gemini Robotics ER（Embodied Reasoning）」で、自然言語の指示からタスクプランニング、視覚的な環境認識、低レベルのモーション生成までをエンドツーエンドで処理する。従来のように知覚モジュール・計画モジュール・制御モジュールを別々に開発し接合する必要性が薄れつつある。

Physical Intelligence（π）は、2025年末の大型資金調達を経て、2026年夏に π-0.5 を発表した。この汎用ロボットファウンデーションモデルは、異なるロボットハードウェア（アーム、モバイルマニピュレータ、ヒューマノイド）間でゼロショット転移を実現し、「1つのモデルで複数の身体を動かす」という長年の夢に現実的な手応えを与えた。Figure や Apptronik といったヒューマノイドスタートアップとの連携も公開されており、倉庫物流での実証実験が複数進行中だ。

一方、Tesla Optimus は独自路線を歩んでおり、自社工場内での部品搬送・検品に特化した形でデプロイ台数を増やしている。汎用性より"確実に動く狭い領域"を優先する戦略は、エンジニアリングとしては極めて堅実だ。

中国勢の台頭も目立つ。Unitree のヒューマノイド「G1/H1」シリーズは価格破壊で研究用途に広く普及し、北京大学や清華大学のラボから次々と成果が出ている。特に、大規模シミュレーション（Isaac Sim / MuJoCo MJX）で学習したポリシーを実機にゼロショット転移する際の Sim-to-Real ギャップの解消手法において、中国発の論文が2026年のトップカンファレンスを席巻している状況は注視に値する。

アーキテクチャパターンの類型化――エージェント設計の"型"が見えてきた

多数のエージェント実装が出揃った今、設計のアーキテクチャパターンをいくつかの型に整理できるようになった。現時点で主流となっているのは、以下の3パターンだ。

パターン1：モノリシック・エンドツーエンド型 単一の大規模マルチモーダルモデルが、知覚・推論・行動生成のすべてを担う。Gemini Robotics ER や Operator Pro の基本構造がこれに近い。モデルの能力がそのままエージェントの能力の上限となるため、基盤モデルの進化に強く依存する。利点はレイテンシの低さとモジュール間のインピーダンスミスマッチがないこと。欠点はデバッグの困難さとハルシネーション時の制御不能リスクだ。

パターン2：オーケストレータ＋専門モジュール型 LLM をオーケストレータ（プランナー）として配置し、GUI認識、OCR、操作実行、検証といった各ステップを専門モジュールに委譲する。CogAgent-2 のリファレンス実装や、LangChain / LangGraph ベースのエージェントフレームワークが典型例。各モジュールを独立にテスト・交換できるソフトウェアエンジニアリング上の利点が大きく、エンタープライズ導入ではこのパターンが依然として主流だ。

パターン3：階層的ポリシー型 主にロボティクスで採用される。高レベルのタスクプランナー（VLM）がサブゴールを生成し、中レベルのスキルポリシーがモーションプリミティブを選択、低レベルのコントローラが関節トルクを出力する。π-0.5 やトヨタ・リサーチ・インスティテュート（TRI）の最新システムはこの構造だ。各階層で異なる時間スケールの意思決定を分離するため、安全性の担保がしやすい反面、階層間のインターフェース設計が煩雑になる。

実際のプロダクトでは、これらの型を純粋に採用するのではなく、ハイブリッドに組み合わせるケースが増えている。たとえば、高レベルのプランニングはエンドツーエンド型の VLM に任せつつ、操作実行部分だけは検証可能な専門モジュールに切り出す、といった構成だ。重要なのは、どのパターンを選ぶかがそのまま安全性とデバッグ容易性のトレードオフに直結するという点である。

安全性課題――「エージェントが暴走する」を防ぐ技術と制度

マルチモーダルエージェントの実用化が進むほど、安全性課題は先鋭化する。GUI操作エージェントは、ユーザーのメールを読み、社内システムにログインし、ファイルを削除できる。ロボティクスエージェントは、物理的に人を傷つけ得る。これはチャットボットのハルシネーションとは次元の異なるリスクだ。

Confirmation Loop（確認ループ）の設計が現時点での最も基本的な防御線だ。Anthropic は Computer Use の GA 版で、不可逆な操作（ファイル削除、送金、メール送信など）の前に必ずユーザー確認を挟む「ガードレール API」を標準搭載した。ただし、確認の頻度が高すぎると自動化の意味がなくなるため、リスクスコアリングに基づく動的な確認閾値の設定が実装上の鍵となる。

サンドボックス実行も広く採用されている。操作をまず仮想環境で実行し、その結果をプレビューした上で実環境に反映する方式で、Operator Pro が「Dry Run モード」として実装している。ロボティクスでは Digital Twin 上でのシミュレーション検証がこれに相当する。

形式検証とランタイムモニタリングのアプローチも注目度が上がっている。2026年春に公開された MIT 発の論文「Safety Shields for GUI Agents」は、エージェントが生成するアクション列に対してリアルタイムで安全性制約（LTL: Linear Temporal Logic で記述）を検証し、違反するアクションをブロックする仕組みを提案した。プロダクション環境での実用にはまだ課題があるが、方向性として重要だ。

制度面では、EU AI Act の全面施行（2026年8月）により、GUI操作エージェントが「ハイリスク AI」に分類される可能性が現実的になっている。特に、金融取引や医療記録へのアクセスを伴うエージェントは、透明性要件・人間の監督要件への適合が求められる。日本国内でも、経産省の「AI 事業者ガイドライン」の2026年改訂版で、エージェント型 AI に関する記述が大幅に拡充される見通しだ。

エンジニアが今やるべきこと

ここまでの議論を踏まえて、実務に携わるエンジニア・研究者が今取るべきアクションを整理しておきたい。

第一に、エージェントフレームワークの選定と習熟だ。LangGraph、CrewAI、AutoGen（Microsoft）、そして Google の Agent Development Kit（ADK）など、主要フレームワークが出揃った。どれを選ぶかは技術的な好みよりも、自社のインフラ（クラウドプロバイダ、使用モデル）との親和性で決めるのが現実的だ。

第二に、評価基盤の構築。エージェントの品質は従来のモデル評価（精度・F値など）では測れない。タスク完了率、操作ステップ数、エラーリカバリ率、安全性違反率といったエージェント固有のメトリクスを定義し、CI/CD パイプラインに組み込む仕組みが不可欠だ。OSS では AgentBench や WebArena の拡張版が利用可能になっている。

第三に、安全性を"後付け"にしない設計思想の内在化。前述の Confirmation Loop、サンドボックス、形式検証は、アーキテクチャの初期設計段階で組み込まなければ機能しない。「まず動くものを作って、安全性は後で」というアプローチは、GUI操作エージェントやロボティクスでは許容されない。

おわりに――2027年に向けた展望

2026年後半、マルチモーダルエージェントは明確に「研究」から「エンジニアリング」の対象に移行した。GUI操作は実用レベルに達し、ロボティクスもファウンデーションモデルの登場で開発パラダイムが変わりつつある。しかし、安全性・信頼性・説明可能性の課題は依然として大きく、ここが次の競争軸になるだろう。

2027年に向けて筆者が注目しているのは、エージェント同士が協調する「マルチエージェントオーケストレーション」の標準化と、物理世界と仮想世界をシームレスに行き来する「ユニバーサルエージェント」の萌芽だ。GUI を操作するエージェントが、必要に応じてロボットアームを呼び出し、物理的な作業を完了させる――そんな未来は、もはや SF ではなく、エンジニアリングロードマップの上にある。

私たちはまさに、エージェントが「道具」から「同僚」に変わる過渡期のただ中にいる。その変化を正しく理解し、安全に実装できるエンジニアの価値は、これからますます高まるはずだ。

EU AI Act全面施行から半年——日本企業が今すぐ対応すべきコンプライアンス実務チェックリスト

2026年8月2日、EU AI Act（人工知能規則）の汎用AIモデル（GPAI）に関する義務規定が全面適用された。施行から約3か月が経過した今、欧州市場向けにサービスを提供する日本企業からは「結局、自社のモデルはどのリスク分類に該当するのか分からない」「モデルカードに何をどこまで書けばいいのか具体的な指針がほしい」という声が絶えない。一方で、欧州AI庁（AI Office）は10月に入り、GPAI向け実施規範（Code of Practice）の最終版を公表し、違反に対する是正命令の第一弾が近いとの観測も広がっている。対岸の火事ではない。本稿では、エンジニアが開発プロセスに"今日から"組み込める実務チェックリストを提示する。

EU AI Actの全体像を30秒でおさらい

リスク分類——実務的な判断基準

エンジニアがまず直面するのは「自社のAIシステムがどのリスクカテゴリに該当するか」という判定作業だ。以下の判断フローを開発初期段階で必ず実施してほしい。

  1. 禁止カテゴリの該当確認: ソーシャルスコアリング、リアルタイム遠隔生体識別（法執行目的の限定的例外あり）、感情推論を職場・教育で行うシステムなどが該当。自社システムの入出力を洗い出し、これらに抵触しないことを文書化する。
  2. ハイリスク判定: Annex IIIに列挙された8分野（生体識別、重要インフラ、教育、雇用、公共サービス、法執行、入管、司法）のユースケースに該当するか精査する。2026年8月以降、ここに該当するシステムは適合性評価・CE マーキング・EU データベース登録が必須となった。
  3. GPAI分類: 汎用目的で提供する基盤モデルは、学習に用いた計算量が10^25 FLOPsを超える場合「システミックリスクを有するGPAI」に分類され、レッドチーミングやモデル評価、サイバーセキュリティ対策、重大インシデント報告の義務が加わる。自社で大規模モデルを訓練していなくても、それをファインチューニングして提供する場合は「デプロイヤー」としての義務が発生する点に注意が必要だ。

モデルカード・技術文書の作成要件

GPAI提供者には、Annex XI/XIIに基づく技術文書の作成と、下流事業者への情報提供が義務づけられている。欧州AI庁が10月に公表した実施規範最終版では、以下の項目が「最低限の記載事項」として明示された。

  • モデルの概要: アーキテクチャ、パラメータ数、学習手法、想定用途と除外用途
  • 学習データの記述: データソースの種類、規模、前処理手法、個人データの有無とGDPR対応状況
  • 評価結果: 標準ベンチマークスコア、バイアス評価、安全性テストの結果と手法
  • 計算資源とエネルギー消費: 学習時・推論時の電力消費量およびCO₂排出推定値
  • 既知の制限事項とリスク緩和策: ハルシネーション率、敵対的攻撃への耐性、監視体制

これらを「モデルカード」としてMarkdown等の機械可読な形式で公開し、バージョン管理する運用体制の整備が求められる。CI/CDパイプラインにモデルカードの自動生成・検証ステップを組み込んでおくと、リリースごとの文書更新漏れを防げる。
